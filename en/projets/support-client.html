A ticketing system where there was none

At Good iD, client requests arrived in individual inboxes, with no number and no tracking. I designed and put into production the set-up the support team uses today: a single address, a tracking spreadsheet and a script that numbers requests, acknowledges receipt and groups follow-ups.

Context and goal

Good iD sells Google Workspace and Google Cloud licences, then supports its clients: migration, training, support. Before July 2026, the company had no centralised system for handling requests. A request could be handled twice, or not at all, without anyone noticing.

The technical lead asked me to design a set-up for the support team and for clients under an operational maintenance contract. The foundations were already there: a Google spreadsheet and a script connected to it were enough, with no external tool and no budget. That is one of the reasons this solution was chosen.

My role

I ran the project from start to finish: defining the conventions (statuses, columns, who updates what), developing the script, writing the onboarding guide, acceptance testing and go-live. Scoping and review were done with the technical lead in two dedicated meetings, on 17 and 20 July.

I did not handle the requests myself: they are dealt with by the support team. My role ended at go-live, about ten days before the end of my internship.

What I did

One address, one spreadsheet, one script

Clients write to a generic support address. Each incoming message creates a row in a Google Sheets spreadsheet: unique ticket number, date, client, subject, message excerpt, status, and a link that opens the thread directly in Gmail. The script sends the acknowledgement with the number, and the whole row takes on the colour of its status.

One ticket per request, not per message

The main difficulty lay in email threads. Without special handling, a client who sends three messages about the same problem generates three tickets, and the spreadsheet becomes unusable within a few weeks. So I wrote reply detection: the script finds the ticket number in the thread, updates the existing row instead of creating a new one, and sets it back to “New” so that it comes back to the team's attention.

Automate the execution, not the judgement

The split is deliberately clear-cut. The script creates the row, assigns the number, sends the acknowledgement, applies the colour and recognises follow-ups. The other three status changes remain manual, because they require judging the real state of a request.

A guide for the next newcomer

A ticketing tool is useless if every newcomer has to ask how to connect to it. I wrote a two-page onboarding guide: setting up Gmail to reply from the support address, reading the spreadsheet column by column, following the lifecycle of a ticket. It stresses a point I had underestimated: checking the “From:” field before every reply. A client who receives a reply from a personal address then replies to that address, and their request drops out of the system.

Acceptance testing and go-live

  • 7 July: first test ticket.
  • 17 and 20 July: scoping and review with the technical lead.
  • 27 July: technical acceptance testing, with several qualification tickets and a check of the support addresses, including one address dedicated to a single client.
  • Early August: go-live.

The system also gained a link in the emails: it carries the ticket number into a Gmail search and leads straight to the relevant thread.

Limitations and what I would do next

  • A bug that shipped. On the first run in the real environment, the notification was not sent: one line of code was still tied to the test environment. Fixed with the technical lead. My takeaway: a script validated in test is not truly validated until it has run once on the account and resources it will actually use.
  • Spotting requests that stall. The spreadsheet shows where a request stands, not for how long. Each status change would need a timestamp to calculate its age.
  • Building knowledge. A “cause” field at closure would show, after a few months, whether requests are similar. I suggested it but did not add it.
  • Maintenance. A one-page note is missing on where the data comes from and what to do in case of failure, especially if the structure of the spreadsheet changes.

On generative AI: Gemini took me from several days to a few hours to get a working script. Internal rules prohibited submitting client data to it, so I described the problems in abstract terms, with fictitious data. Time saved on writing code must be reinvested in testing: that is the rule I have set myself ever since.
